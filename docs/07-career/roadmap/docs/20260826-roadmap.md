> 2026-08-26, 새로운 조사 자료를 근거로 기존 2026 로드맵의 방향을 전면 재검토하고 수립한 로드맵입니다. 메인 목표가 "기술 스택 확장"에서 **"이직"**으로 명확화되었고, 이후 모든 학습·개발 우선순위는 이 목표에 종속됩니다. **실행 시작 시점은 9월입니다.**

## 📌 배경 — 왜 로드맵을 다시 짰나

- 기존 로드맵(.NET 10 & Azure)은 "기술 스택을 순서대로 넓힌다"는 방향이었으나, 목표가 없는 확장은 방향성이 흐려짐을 인지
- 시장 조사 결과 **"C#/.NET 진영 대기업"이라는 전제 자체가 국내 현실과 어긋남** — 금융권은 Java/Spring 압도적, 대형 게임사 서버도 C++/Java/Go 위주. C#/.NET은 제조 MES/ERP, SI/솔루션, 소수 게임 스튜디오, AI/SaaS 스타트업 등 **니치 시장**
- 그중 **넥슨코리아 플랫폼본부(구 인텔리전스랩스) 빌링/플랫폼 공통서비스**가 요구 스펙·연차·도메인 정합성 면에서 가장 구체적이고 반복적으로 확인된 타겟
- 이 타겟 기준으로 클라우드(Azure→AWS), DB, 미니 프로젝트 도메인(주문/재고 → 재화 충전/과금) 등 다수 항목이 기존 계획과 충돌 → 재정렬

## 🎯 목표 및 타겟

- **메인 목표**: 이직
- **1순위 타겟**: 넥슨코리아 플랫폼본부 > 플랫폼파운데이션그룹 (구 인텔리전스랩스 빌링팀 — 인증·계정·빌링 등 핵심 공통 서비스), 인접 조직(NCS개발팀 / 라이브웹개발팀 / 운영플랫폼팀)도 병행 모니터링
- **현재 상태**: C#/.NET 10년차·과장급, MSSQL/SP 실무 경험, ASP.NET MVC5 실무 경험(리팩토링), Minimal API 학습 중(22편)
- **참고**: 넥슨은 상시채용 성격이 강해 "빌링팀"이라는 이름으로 공고가 안 뜨더라도 "플랫폼본부/플랫폼파운데이션그룹/인증/세션" 키워드로 모니터링 필요

## 🧭 핵심 포지셔닝 — "무기" 정의

> **"C# 언어" 자체가 아니라 "결제 도메인 역량"이 무기다.**

결제/빌링 백엔드는 언어와 무관하게 아래 5가지로 수렴한다는 것이 조사 결론:

1. 멱등성(Idempotency)
2. 동시성 제어
3. 트랜잭션 정합성 (아웃박스/보상 트랜잭션)
4. RDBMS 모델링/최적화
5. 대용량 트래픽 대응

SP(저장 프로시저) 실무 경험은 약점이 아니라 **차별화 자산**으로 포지셔닝. 다만 EF Core/Dapper와 SP를 "언제, 왜" 구분해 쓰는지 판단 근거를 설명할 수 있어야 함(면접에서 ORM 이해도 부족이 감점 요인이 된 경험 있음). 특히 ORM은 "사용 경험"이 아니라 **트랜잭션·동시성 등 문제 해결 능력**을 검증받는다는 점을 인지.

> ※ **정직성 각주**: Kafka·Redis·Docker·CloudWatch·DDD·Grafana 등 모던 스택은 넥슨의 **Java 계열 플랫폼 공고**에서 확인된 것이며, **C# 빌링 공고에는 ORM·Redis·Kafka·CloudWatch가 명시된 바 없음(전부 "미확인")**. CloudWatch "우선"은 넥슨 C# 공고 근거가 아니라 AWS 일반 베스트프랙티스에 따른 선택임. C# 빌링 공고에서 확인된 키워드는 **C#/.NET Framework, SQL Server/MySQL, TCP/IP, HTTP, WebAPI, AWS**뿐.

> 💡 C# 10 학습분(45편)과 Minimal API 학습분(22편)은 폐기되는 것이 아니라 그대로 자산화됩니다. 바뀌는 것은 **이후 우선순위**입니다.

## 📦 미니 프로젝트: 재화 충전·차감 API (최소 버전)

**목적**: "이것저것 배웠다"가 아니라 **"결제 도메인의 핵심 문제(멱등성·동시성·트랜잭션)를 실제로 해결해본 사람"**이라는 서사를 만드는 것.

### 한 줄 정의

> 재화 충전/차감 API. 단, **멱등성·동시성·트랜잭션을 제대로 처리한 것.**

기능은 딱 3개. 그러나 이 3개 안에 넥슨 빌링이 요구하는 핵심이 모두 들어감. **"기능 많이"가 아니라 "이 3개를 깊게"가 원칙.**

### 스택 (최소)

- ASP.NET Core Web API (.NET 최신)
- **MSSQL 하나만** (MySQL은 확장 단계에서 추가)
- 충전/차감(원장/명령) = **SP + Dapper 호출** (본인 강점)
- 잔액·유저 등 도메인 상태 = **EF Core Fluent API** (모델링·마이그레이션·변경 추적·동시성 토큰까지 실제 활용 — ORM 문제 해결력 증명. "최소"가 아니라 "판단 근거를 보여줄 만큼"은 제대로 다룸)
- 로컬 실행 (AWS 배포는 확장 단계)

### MVP 핵심 API (딱 3개)

| API | 기능 | 증명하는 역량 | 데이터 접근 |
| :--- | :--- | :--- | :--- |
| `POST /wallet/charge` | 재화 충전 | **멱등성** (Idempotency-Key, 중복 충전 차단) | SP + Dapper |
| `POST /wallet/consume` | 재화 차감 | **동시성** (락으로 잔액 음수 방지) | SP + Dapper |
| `GET /wallet/{id}` | 잔액/거래 이력 조회 | **조회 최적화** (Dapper) | Dapper |

### 심을 것 (깊이 — 이게 진짜 핵심)

1. **멱등성** — 충전 API에 `Idempotency-Key` 헤더. 같은 키로 두 번 오면 두 번째는 저장하지 않고 첫 결과 반환. (토스페이먼츠 멱등키 규격 참고: UUID·TTL, 처리 중 재요청 409, 완료 재요청은 최초 결과 재반환)
2. **동시성** — 같은 유저가 동시에 차감 → 잔액이 음수가 되는 상황을 **일부러 재현**하고, 낙관적/비관적 락으로 해결. Before(터짐)/After(막힘)를 로그로 남김.
3. **트랜잭션** — 차감 + 이력 기록을 하나의 트랜잭션으로 묶고, 중간 실패 시 롤백되는 것을 검증.

### 기록 방식

README에 각 항목을 **"문제 → 원인 → 해결 → 결과"** 형식으로 서술 → 면접 소재로 그대로 사용.

또한 **TCP/IP·HTTP 이해 증명**: 코드로 보여주기 어려운 항목이므로 README에 "HTTP 상태 코드 설계 근거", "멱등성을 PUT vs POST 시맨틱 관점에서 어떻게 반영했는지", "재시도/타임아웃 처리의 TCP 커넥션 관점 판단"을 서술. 이 서술이 지원 임박 시 기본기 2주 온보딩의 복습 자료가 됨.

### 하지 않는 것 (스코프 제외)

프론트 UI, 보안키패드, 실제 PG 연동, 정산 시스템, 환불, BFF, SignalR, 실시간 알림 — **전부 제외 또는 확장 단계로 미룸.**

| 확장 2 | CI/CD 자동화 + CloudWatch 모니터링 | "운영까지 해본" 서사 |

## 🗓️ 로드맵 (9월~10월 상세, 11월~ 방향성)

**3개 축**: 메인(미니 프로젝트, 여유 주에 집중 구현) / 서브1(코딩테스트, 매일 1문제) / 서브2(AWS, 인강 위주 여유 있게)

> **데이터 접근 이원화(원칙)**: 명령/거래(충전·차감)는 **SP + Dapper**, 도메인 상태(Wallet·유저 등)는 **EF Core**로 관리. "언제 SP를, 언제 ORM을 쓰는가"를 코드로 증명하는 것이 ORM 감점 방어의 핵심.

| **10월 3~4주차 — 정리** | 조회 API + Dapper 최적화, 아키텍처 다이어그램 정리 · **EF Core N+1 재현 → Dapper 전환 비교(ORM 판단력 실증)** | 매일 1문제 | Docker 컨테이너화 시작 (배포 준비) |
| **11월~ (방향성만)** | 확장 단계(MySQL 분리 → AWS 배포 → CI/CD → CloudWatch → 장애 시나리오), AWS 자격증 본격화 | 유지 | 유지 |
| **지원·면접 임박 시** | **기본기 2주 집중 온보딩**: HTTP/TCP/OS를 "화이트보드에서 설명 가능한 수준"으로 정리 (프로젝트 중 메모해둔 것 복습 위주) | | |

> 💡 **EF Core 트랙 요약 (면접 소재 4종)**: ① 도메인 모델링+마이그레이션 → ② 변경 추적 기반 상태 관리 → ③ 동시성 토큰 vs SP 락 비교 → ④ N+1 재현→Dapper 전환. 이 4개가 "ORM 사용 경험"을 넘어 "ORM 문제 해결력"을 증명하는 핵심 서사.

## ⚙️ 운영 원칙

1. **여유 2주 = 구현, 바쁜 2주 = 문서·복습·인강.** 바쁠 때 코드 진도가 멈춰도 정상.
2. **순연은 실패가 아니라 기본값.** 실무가 터지면 해당 단계를 통째로 미룬다. 위 일정은 마감이 아니라 가이드.
3. **코테와 AWS는 프로젝트와 시간대 분리.** 코테=아침(매일 1문제), 프로젝트=저녁/주말, AWS=여유 있게 인강.
4. **가장 중요한 마일스톤은 단 하나 — MVP(멱등성·동시성·트랜잭션이 들어간 충전/차감 API).** 완성되면 이미 지원 가능 상태.
5. **공고가 MVP 전에 뜨면?** "개발 중" 상태로라도 지원. 넥슨은 상시채용이라 다음 기회도 있음.

## 📢 기존 로드맵과의 관계
